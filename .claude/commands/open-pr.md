You are in PR MODE. Follow these steps in order. Stop and report if any step fails.

## Step 0: Determine the base branch

Do NOT assume `main`. Stacked branches happen, so the base can be another
feature branch. Detect the most likely base (the local branch with the closest
merge-base to HEAD) and confirm it with the user before continuing:

```bash
CURRENT=$(git branch --show-current)
git for-each-ref --format='%(refname:short)' refs/heads/ \
  | grep -vx "$CURRENT" \
  | while read -r b; do echo "$(git rev-list --count "$b..HEAD") $b"; done \
  | awk '$1+0 > 0' | sort -n | head -5
```

The branch with the smallest commit count is the likely base. Tell the user the
detected base and how many commits the PR would contain (`git rev-list --count
<base>..HEAD`), and confirm before proceeding. Use this value as `<base>` in
every command below. Also verify the base exists on origin and is current
(`git rev-list --count origin/<base>..<base>`); if origin's base is behind, the
base must be pushed first or the PR diff will be wrong.

## Step 1: Pre-flight checks

Determine changed files with `git diff <base>...HEAD --name-only`, then run
every applicable group.

### Always (Python data layer)
```bash
uv run ruff check . && uv run ruff format --check .
uv run mypy
uv run pytest -q
uv run syscards schema --check
```

If `ruff format --check` fails, run `uv run ruff format .`, commit the
formatting changes, then re-verify. If `schema --check` fails, run
`uv run syscards schema`, commit, re-verify.

### Data (if any `sources/` or `normalization/` file changed)
```bash
uv run syscards fetch-all
uv run syscards check --require-pdfs
```

If a document host is unreachable from here, say which, run
`uv run syscards check` without `--require-pdfs`, and state in the PR body
that those quotes were not verified in this session.

### Site (if any `site/` file changed)
```bash
cd site && npm ci && npm run lint && npm run typecheck && npm run test && npm run build
```

**If any check fails, stop and report the failure. Do not proceed to PR
creation.**

## Step 2: Craft PR title and description

1. `git log <base>...HEAD --oneline`
2. `git diff <base>...HEAD --stat`
3. Check for GitHub issue references in commit messages or the branch name
4. Read key changed files if needed to understand the scope

### Title
- Short, descriptive (under 70 chars)
- Conventional prefix: `feat:`, `fix:`, `data:`, `refactor:`, `docs:`, `chore:`
- `data:` PRs name the card: `data: add Claude Opus 4.8 system card (2026-05)`

### Body
```
## Summary
<2-4 bullet points describing what changed and why>

## Changes
<Bulleted list of specific changes grouped by area (schema, check, build, CLI, cards, site, docs)>

## Cards
<data PRs only: one row per card: id · document title · sha256 (first 12) · pages · cites verified · verification: none · bytes from (lab | mirror URL)>

## Tickets
<Referenced issues, or "None">

## Testing
<Exactly what ran and what did not. "Quotes verified locally against the cached PDF; CI's offline job does not verify quotes." Never "all checks pass" for a check that did not run.>

## Deploy Notes
<"Publishes to Pages on merge" once the Pages workflow exists, or "None">
```

**IMPORTANT:** Do NOT include any mention of Claude Code, AI, or "generated by"
in the PR title or body. The PR should read as if written by the developer.

## Step 3: Push and create PR

Do NOT ask for permission to push or review the PR description. Proceed directly:
1. Push the branch to origin (with `-u` if needed)
2. Create the PR (GitHub MCP `create_pull_request`, owner `mdworkin21`, repo
   `system-cards`, or `gh pr create`)
3. Return the PR URL
